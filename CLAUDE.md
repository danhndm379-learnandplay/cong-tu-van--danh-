## Tổng quan

DuHoc24 — website mẫu "Cổng Tiếp Nhận Hồ Sơ Du Học" cho khoá lập trình 6 tuần. Dự án đã vượt giai đoạn UI tĩnh: có chatbot Gemini lưu hội thoại vào Supabase, trích xuất lead, trang điểm chuẩn công khai, và cổng hồ sơ học viên (upload giấy tờ → Gemini đọc → kiểm tra đủ/thiếu → đối chiếu điểm chuẩn → AI gợi ý học bổng). Một số trang admin (`profiles`) vẫn dùng mock data trong `lib/mock-data.ts`. Đã có đăng nhập bằng magic link (trang `/login`, Supabase Auth) và hồ sơ học viên đã gắn với tài khoản, bảo vệ bằng RLS (xem các mục dưới). Lộ trình các tuần nằm trong `README.md`.

Nội dung giao diện, tên biến trạng thái và comment đều bằng tiếng Việt (`lang="vi"`, font Be Vietnam Pro). Giữ nguyên quy ước này khi thêm UI/copy mới.

## Commands

```bash
npm install
npm run dev     # dev server tại http://localhost:3000
npm run build   # production build (cũng chạy type-check)
npm run start   # chạy bản build
npm run lint    # ESLint 9 (flat config, eslint.config.mjs)
```

`npm test` chạy bộ test logic thuần bằng bộ chạy test có sẵn của Node (thư mục `tests/*.test.mjs`, import thẳng file `.ts` nhờ type stripping của Node 24; chỉ test các module KHÔNG có import runtime/alias `@/`: `portal-docs`, `school-match`, `upload-validation`, `lead-sanitize`, `leads-csv`, `scholarship-format`, `scholarship-advice`, `quote`, `auth-redirect`). Module mới có logic quyết định (đạt/chưa đạt, hợp lệ/không) nên viết dạng thuần như vậy để test được. Chatbot cần `GEMINI_API_KEY`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY` trong `.env.local` (xem hội thoại ở admin cần thêm `ADMIN_PASSWORD`) (copy từ `.env.example`; file này đã được gitignore). Thiếu key thì `/api/chat` báo lỗi, phần còn lại của site vẫn chạy.

## Kiến trúc

- **Next.js 16 App Router + React 19 + TypeScript strict + Tailwind CSS v4.** Version này có breaking changes so với kiến thức cũ — đọc `node_modules/next/dist/docs/` trước khi viết code Next.js (xem `AGENTS.md`). Ví dụ: layout dùng type helper toàn cục `LayoutProps<"/">` thay vì tự khai báo props.
- **Path alias:** `@/*` trỏ về root repo (ví dụ `@/components/ui/button`, `@/lib/mock-data`).
- **Ba khu vực route:**
  - `/` — landing page ghép từ `components/landing/*` (hero, quote-form, highlights, chat-widget) cùng `site-header`/`site-footer`.
  - `/portal` — cổng học viên, ghép từ `components/portal/*`, bắt buộc đăng nhập, chỉ đọc hồ sơ của chính người dùng (RLS).
  - `/admin/*` — dùng chung `app/admin/layout.tsx` (sidebar + mobile nav); `/admin` redirect sang `/admin/requests`. Các page con: `requests`, `schools`, `profiles`, `conversations`.
- **Server Component là mặc định.** Các page admin/portal là Server Component import thẳng từ `lib/mock-data.ts`; chỉ những component cần state/tương tác mới có `"use client"` (`site-header`, `admin/sidebar`, `landing/quote-form`, `landing/chat-widget`, và vài wrapper trong `ui/`).
- **`lib/mock-data.ts` chỉ còn là nguồn dữ liệu giả cho phần chưa nối Supabase** (admin `profiles`, danh sách quốc gia và mô tả gói dịch vụ của form báo giá). Danh sách trường và hồ sơ học viên đã chuyển sang Supabase. Chứa các type (`DocStatus`, `RequestStatus`, `ServicePackage`, `School`, `AdmissionRequest`, `StudentProfile`, `Conversation`, ...) và dữ liệu mẫu. Giá trị enum là slug tiếng Việt không dấu (`cho_duyet`, `hop_le`, `co_ban`, ...). Khi nối Supabase ở các tuần sau, thay dữ liệu và giữ nguyên các type này nếu có thể để UI không phải đổi theo.
- **Hiển thị trạng thái:** `components/status-badge.tsx` map `DocStatus`/`RequestStatus` sang tone màu + icon; dùng lại thay vì tự tạo badge mới.
- **Chatbot (Gemini):** `landing/chat-widget.tsx` (client) POST toàn bộ lịch sử hội thoại tới route handler `app/api/chat/route.ts`, nơi gọi `@google/genai` với `systemInstruction` được dựng từ bộ QnA trong `lib/chatbot-qna.ts`. Persona, luồng hội thoại và thông tin dịch vụ (dịch vụ, trụ sở, hotline) nằm ở `lib/chatbot-prompt.ts` (sửa ở đó để đổi cách bot nói chuyện). Bot là trợ lý tư vấn dẫn dắt theo 7 bước: hỏi nước → bậc học/ngành → giới thiệu dịch vụ → hỏi muốn tìm hiểu thêm → thu thập lần lượt họ tên, email, số điện thoại → mời tư vấn miễn phí → hỏi ghi chú cuối. Mỗi lượt chỉ một câu hỏi, tối đa 2-3 câu, không nói về chi phí trừ khi khách hỏi, không cam kết đậu visa/học bổng. Câu khớp bộ QnA thì trả lời theo bộ này; câu ngoài bộ thì trả lời bằng kiến thức chung kèm ghi chú "tham khảo, không chính thức" rồi quay lại luồng; không bao giờ từ chối. Chỉ khẳng định về DuHoc24 những gì có trong `companyInfo` và bộ QnA. Bot KHÔNG đặt được lịch: prompt cấm nói/ngụ ý đã đặt, ghi nhận, xác nhận hay giữ chỗ lịch hẹn (mục "VỀ ĐẶT LỊCH"), chỉ hướng dẫn gọi hotline/đến trụ sở. Lưu ý: không viết câu mẫu tiếng Việt vào quy tắc của prompt, model lite sẽ bắt chước và trả lời tiếng Việt cho câu hỏi tiếng Anh. API key chỉ nằm phía server (`GEMINI_API_KEY`, `GEMINI_MODEL` trong `.env.local`, mặc định `gemini-3.5-flash-lite`). Tên model Gemini bị Google retire thường xuyên (`gemini-2.5-flash` đã trả 404) — nếu gặp 404 thì liệt kê model bằng `ai.models.list()` rồi đổi `GEMINI_MODEL`. Cấu trúc chatbot:
  - `lib/chatbot-qna.ts`: bộ QnA; cờ `suggested` → nút gợi ý trong widget, cờ `fallback` → câu dùng khi hỏi ngoài phạm vi (prompt lấy từ cờ này, không trỏ theo chữ của câu hỏi).
  - `lib/chatbot-config.ts`: type `ChatMessage`, giới hạn (độ dài, số lần retry), lời chào và thông điệp lỗi song ngữ Việt/Anh. Server chỉ trả **mã lỗi** (`rate_limited`, `upstream_busy`, ...), widget tra thông điệp ở đây.
  - `lib/rate-limit.ts`: limiter in-memory (mặc định 10 req/phút/IP + 12 req/phút toàn site, vì gói free Gemini chỉ cho 15 req/phút/model, chỉnh bằng env `CHAT_RATE_LIMIT_PER_MIN`, `CHAT_GLOBAL_RATE_LIMIT_PER_MIN`). Trên serverless mỗi instance có bộ nhớ riêng nên chỉ gần đúng; IP lấy từ `x-forwarded-for`.
  - `route.ts` chuẩn hoá lịch sử do client gửi (cắt độ dài, gộp lượt trùng vai, bắt đầu/kết thúc bằng lượt user). Client gửi cả lượt bot nên về nguyên tắc có thể bị giả mạo — chấp nhận được vì user vốn tự gõ được mọi thứ; muốn chặt hơn phải lưu hội thoại phía server (Tuần 3).
  - Ngôn ngữ: model phải khai báo `user_language` trước rồi mới viết `reply` (structured output JSON), nhờ vậy trả lời đúng ngôn ngữ người dùng mà không cần dò ngôn ngữ trong code. Tiếng Anh/Việt ổn định; tiếng Nhật/Hàn với model lite còn sai. Bị lỗi 429/503 từ Google thì route trả `upstream_busy` (503 được retry tối đa 3 lần).
  - `temperature: 0` và `ThinkingLevel.MINIMAL` (chỉnh qua `GEMINI_THINKING_LEVEL`) để trả lời nhanh (~1s); không phải model nào cũng hỗ trợ `MINIMAL` (`gemini-3.8-flash` từ chối).
- **Lưu hội thoại chatbot (Supabase):** mỗi cuộc trò chuyện lưu ở bảng `conversations`/`messages` (migration: `supabase/migrations/`). Đây là dữ liệu riêng tư: RLS bật, `anon`/`authenticated` bị thu hồi quyền và có policy `using (false)`, chỉ `service_role` truy cập được — không bao giờ thêm policy cho phép trình duyệt đọc/ghi, và không đọc các bảng này bằng publishable key. Mọi truy cập đi qua `lib/chat-store.ts` (có `import "server-only"`, dùng `createAdminClient` của `@supabase/server/core` với `SUPABASE_URL` + `SUPABASE_SECRET_KEY`). Khách được nhận diện bằng cookie httpOnly `duhoc24_visitor` (token ngẫu nhiên; DB chỉ lưu sha256). `GET /api/chat` trả lịch sử của khách, `POST /api/chat` nhận **một** câu `{ message }`, lấy lịch sử từ DB (không tin lịch sử từ trình duyệt), gọi Gemini, lưu cả hai tin rồi trả lại đúng các dòng đã lưu. Widget không lưu gì ở `localStorage`. Chưa có đăng nhập khách nên chưa gắn hội thoại với tài khoản. Trang `/admin/conversations` (danh sách, phân trang 20/trang) và `/admin/conversations/[id]` (toàn bộ tin nhắn) đọc **dữ liệu thật** từ DB qua `listConversationsForAdmin`/`getConversationForAdmin` (RPC `list_conversations_for_admin`, chỉ `service_role` gọi được) và đăng nhập là **tuỳ chọn** (hiện đang TẮT, tức ai biết URL cũng xem được hội thoại của khách): đặt `ADMIN_PASSWORD` (và `ADMIN_USER`, mặc định `admin`) để bật HTTP Basic Auth. Khi bật, `proxy.ts` hiện hộp thoại đăng nhập và mỗi trang tự gọi `requireAdmin()` (`lib/admin-guard.ts`) phòng khi proxy bị bỏ qua; mọi trang/route mới đọc dữ liệu hội thoại phải gọi `requireAdmin()` và thêm vào matcher của `proxy.ts`. Admin xoá được cuộc trò chuyện (nút "Xoá" ở danh sách và chi tiết, có bước xác nhận) qua Server Action `deleteConversationAction` (`app/admin/conversations/actions.ts`) → `deleteConversationForAdmin` (xoá vĩnh viễn, tin nhắn xoá theo nhờ `on delete cascade`); action tự kiểm tra quyền bằng `checkAdminWrite()` vì Server Action là endpoint công khai. Hiện chưa bật đăng nhập nên **ai biết URL cũng xoá được hội thoại**; đặt `ADMIN_PASSWORD` để chỉ admin xoá được. **Lead:** ở trang chi tiết mỗi cuộc trò chuyện có thẻ "Thông tin lead" (`components/admin/lead-card.tsx`) và nút "Trích xuất lead"/"Trích xuất lại" gọi Server Action `extractLeadAction` (`app/admin/conversations/actions.ts`): đọc toàn bộ tin nhắn từ DB, gọi Gemini (`gemini-3.1-flash-lite`, env `GEMINI_LEAD_MODEL`) với structured output ở `lib/lead-extraction.ts` để lấy tên, email, số điện thoại, nước du học, bậc học, ngành, availability, đặt lịch tư vấn (true/false/null), note, chất lượng (`good`/`ok`/`spam`) rồi lưu vào bảng `leads` (`lib/lead-store.ts`; một lead cho mỗi cuộc, ghi đè khi trích xuất lại, xoá theo khi xoá cuộc trò chuyện nhờ `on delete cascade`). Bảng `leads` có PII nên cũng RLS-bật, anon/authenticated bị chặn, chỉ `service_role` truy cập. Kết quả của model LUÔN đi qua `sanitizeLead` (`lib/lead-sanitize.ts`, hàm thuần có test trực tiếp bằng Node): email/số điện thoại chỉ được giữ nếu thật sự nằm trong lời của KHÁCH (chặn bịa và chặn lấy nhầm hotline của chatbot), và `good` bắt buộc có ít nhất một thông tin liên hệ hợp lệ. Trang danh sách có cột chất lượng lead (`LeadQualityBadge`), bộ lọc `?quality=good|ok|spam|none` (`none` = chưa trích xuất; giá trị lạ = không lọc; xử lý ở RPC `list_conversations_for_admin`/`count_conversations_for_admin`, parse bằng `parseQualityFilter`) và nút "Xuất CSV lead" → route `app/admin/conversations/export/route.ts` (`listLeadsForExport` + `leadsToCsv` ở `lib/leads-csv.ts`: có BOM UTF-8 và chống CSV/formula injection vì tên/ghi chú do khách nhập; route tự kiểm tra đăng nhập nếu bật và nằm trong matcher của `proxy.ts`). Trích xuất do admin bấm tay (không tự chạy khi mở trang), có giới hạn 6 lần/phút/IP và 10 lần/phút toàn site, tách riêng với giới hạn của chatbot. Khu vực `/admin` có `robots: noindex` nhưng đó không phải bảo vệ. Đây là giải pháp tạm; thay bằng Supabase Auth ở Tuần 6. Các trang admin khác (`profiles`) vẫn dùng mock data và chưa có đăng nhập.
- **Trường tham chiếu và học bổng (dữ liệu CÔNG KHAI):** bảng `schools` (tên, quốc gia, điểm học tập tối thiểu thang 10, IELTS tối thiểu) và `scholarships` (tên, trường, điều kiện = chỉ tiêu `gpa`|`ielts` + ngưỡng, mức hỗ trợ = phần trăm|toàn phần). RLS: `anon`/`authenticated` chỉ được SELECT (policy `using (true)`), mọi quyền ghi bị thu hồi, chỉ migration/`service_role` ghi được. Đọc bằng client ẩn danh `lib/supabase-public.ts` (publishable key; nếu thiếu `SUPABASE_PUBLISHABLE_KEY` thì tự dùng secret key phía server và ghi cảnh báo) qua `lib/school-store.ts`. Hai trang đọc dữ liệu thật: `/schools` (công khai, link "Điểm chuẩn trường" ở menu/footer) và `/admin/schools`; cả hai gọi `await connection()` để không bị prerender lúc build. Các nút Thêm/Sửa/Xoá ở `/admin/schools` mới chỉ là UI.
- **Cổng hồ sơ học viên `/portal` (dữ liệu RIÊNG TƯ, có PII):** luồng `POST /api/portal/documents` (mỗi request một file, tối đa 4 MB vì giới hạn body ~4.5 MB của Vercel): (1) `lib/upload-validation.ts` kiểm tra dung lượng và định dạng THẬT bằng magic bytes (bảng điểm chỉ PDF; IELTS và CMND/hộ chiếu chỉ ảnh JPG/PNG/WebP); (2) `lib/document-extraction.ts` gửi file thẳng cho Gemini (đa phương thức) với structured output theo schema từng loại, model `GEMINI_DOC_MODEL` mặc định `gemini-3.1-flash-lite`; (3) `sanitizeDocFields` (`lib/portal-docs.ts`) làm sạch kết quả, giá trị không hợp lệ thành null thay vì đoán; (4) lưu vào `student_profiles`/`student_documents` qua `lib/student-store.ts` (**file gốc không được lưu**, chỉ lưu thông tin trích xuất và tên/loại/dung lượng file). **Hồ sơ gắn với TÀI KHOẢN đăng nhập và bảo vệ bằng RLS (`supabase/migrations/20261031080000_student_profiles_row_level_security.sql`):** `student_profiles.user_id` (unique, `references auth.users on delete cascade`, bỏ cột `owner_token_hash` và cookie `duhoc24_student`). Policy: `anon` không có quyền gì; `authenticated` chỉ có SELECT và chỉ hàng của mình (`user_id = (select auth.uid())`; giấy tờ qua `exists` tới hồ sơ của mình), KHÔNG có quyền ghi (điểm số do AI đọc nên chỉ server mới ghi, người dùng không tự sửa được). Code: ĐỌC bằng phiên của chính người dùng (`loadStudentSnapshot(userId)` dùng `createAuthClient()` ở `lib/supabase-auth.ts`, role `authenticated`, kèm `.eq("user_id")` làm lớp thứ hai), GHI bằng secret key (`getOrCreateStudentProfile(userId)`, `saveStudentDocument`, `saveScholarshipSuggestions(userId, ...)`) với `userId` lấy từ `getCurrentUser()` (phiên đã được Supabase xác thực), KHÔNG BAO GIỜ từ dữ liệu client gửi. `/portal` bắt buộc đăng nhập: chưa đăng nhập thì `proxy.ts` (chặn sớm, kể cả cookie phiên giả/hết hạn) và `page.tsx` (`redirect("/login")`) chuyển sang `/login`; `POST /api/portal/documents` và `/api/portal/scholarships` trả 401 (client tự chuyển sang `/login`). Kiểm tra lại RLS bằng `node scripts/check-rls.mjs` (tạo 2 người dùng thử trên database thật, thử đọc/ghi chéo bằng token thật qua REST, rồi xoá; không gửi email). Trích xuất: bảng điểm = họ tên, ngày sinh, điểm tổng kết + thang điểm; IELTS = họ tên, 4 kỹ năng, Overall, ngày thi; CMND/hộ chiếu = họ tên, ngày sinh, số giấy tờ. Giấy tờ nộp lại thay thế bản cũ cùng loại; file bị từ chối TRƯỚC khi đọc (sai định dạng, rỗng, quá lớn) hoặc lỗi hệ thống thì KHÔNG ghi đè bản đã nộp.
- **Kiểm tra đủ/thiếu/hợp lệ = code thường, không hỏi lại AI** (`evaluateDocument`/`evaluateProfile` trong `lib/portal-docs.ts`): giấy tờ hợp lệ khi mọi trường bắt buộc (`REQUIRED_FIELDS`) đọc được và qua vài phép kiểm tra nhất quán (ngày sinh/ngày thi không ở tương lai, điểm tổng kết không vượt thang, điểm Overall IELTS khớp trung bình 4 kỹ năng làm tròn 0.5). Thông báo nêu rõ thiếu giấy tờ nào, file nào cần nộp lại, trường nào không đọc được; lời khuyên chụp lại (`RESUBMIT_TIPS`) tách riêng để UI chỉ hiện một lần. `ProfileStatus` (banner) và `DocumentUploadCard` (từng thẻ) hiển thị.
- **Đối chiếu điểm chuẩn = phép so sánh số, không dùng AI** (`lib/school-match.ts`, chỉ chạy khi hồ sơ đủ và hợp lệ): đạt khi điểm học tập (quy đổi tuyến tính về thang 10 nếu giấy tờ dùng thang khác; so sánh bằng số nguyên `gpa*100*10 ≥ minGpa*100*scale` để không sai số thực) VÀ IELTS Overall đều ≥ điểm chuẩn. Giao diện ghi rõ số liệu hai vế từng tiêu chí để kiểm tra lại.
- **Gợi ý học bổng bằng function calling** (`lib/scholarship-advisor.ts`, `POST /api/portal/scholarships`, chạy khi hồ sơ đủ và có ít nhất một trường đạt): chỉ gửi cho AI các con số học tập (không gửi họ tên/ngày sinh/số giấy tờ) cùng danh sách trường đã đạt; AI có MỘT công cụ `search_scholarships(school_name)`, TỰ quyết định tra cứu trường nào và TỰ kết luận đủ điều kiện hay không (code không có luật so sánh điều kiện học bổng); câu trả lời cuối là JSON theo schema (function calling kết hợp được với structured output trên model này). Code chỉ thực thi công cụ, kiểm tra học bổng AI nhắc tới phải có trong dữ liệu công cụ trả về, và hiển thị điều kiện/mức hỗ trợ lấy từ database cạnh nhận định của AI. Kết quả lưu đệm trong `student_profiles.scholarship_suggestions` kèm `scholarship_input_hash` (hồ sơ + trường đạt + dữ liệu học bổng); `ScholarshipPanel` tự gọi một lần khi chưa có bản còn khớp. Không có trường nào đạt thì không gọi AI.
- **Phân biệt kỹ thuật (đừng nhầm):** đa phương thức = đưa PDF/ảnh vào model (đọc giấy tờ); structured output = ép model trả JSON đúng schema (trích xuất giấy tờ, lead, câu trả lời cuối của advisor); function calling = model tự gọi công cụ do ta cung cấp rồi dùng kết quả (advisor tra học bổng); code thường = mọi quyết định cần chính xác và kiểm tra lại được (đủ/thiếu giấy tờ, đạt/chưa đạt điểm chuẩn, kiểm chứng đầu ra của AI). Xem docs/ghi-chu-ho-so-hoc-vien.md.
- **Đăng nhập bằng magic link (Supabase Auth, `docs/ghi-chu-dang-nhap.md`):** `/login` (`app/login/page.tsx` + `components/auth/login-form.tsx`, noindex, đã đăng nhập thì chuyển `/portal`) → Server Action `sendMagicLinkAction` (`app/login/actions.ts`: kiểm tra email bằng `isValidEmail`, giới hạn 5/phút/IP + 1/phút/email + 25/giờ toàn site, `signInWithOtp` với `emailRedirectTo = <origin>/auth/callback`, luôn trả lời giống nhau dù email đã có tài khoản hay chưa) → email qua Gmail SMTP đã cấu hình ở Supabase → `app/auth/callback/route.ts` (GET): nhận `?code=` (PKCE, phải mở link ở CÙNG trình duyệt) hoặc `?token_hash=&type=email|magiclink` (khi đã sửa mẫu email, mở được ở thiết bị khác) rồi đổi sang phiên và chuyển tới `next` (chỉ nhận đường dẫn nội bộ, `safeNextPath`); lỗi thì về `/login?error=link_invalid|link_expired|not_configured`. Thư viện `@supabase/ssr` quản lý cookie phiên `sb-<project>-auth-token`, được đặt `httpOnly` (+`secure` ở production) qua `sessionCookieOptions` vì site chỉ dùng phiên ở server; client là `createAuthClient()`/`getCurrentUser()` ở `lib/supabase-auth.ts`, dùng `SUPABASE_URL` + `SUPABASE_PUBLISHABLE_KEY` (BẮT BUỘC cho đăng nhập, không dùng secret key để tạo phiên người dùng; `lib/auth-env.ts`). `proxy.ts` làm hai việc theo đường dẫn: Basic Auth tuỳ chọn cho các trang `/admin/...` có dữ liệu khách, và làm mới token Supabase cho `/portal` và `/login` (chỉ khi có cookie phiên), riêng `/portal` còn chuyển người chưa đăng nhập sang `/login`. `UserBar` ở đầu `/portal` hiện email đang đăng nhập + nút Đăng xuất (`signOutAction`). **Chưa làm:** hiện bất kỳ email nào cũng đăng nhập được (Supabase tự tạo người dùng); admin chưa dùng tài khoản. Cần cấu hình ở Supabase Dashboard: Site URL + Redirect URLs có `/auth/callback` (xem docs). Khi sửa `lib/auth-env.ts` rồi thấy cookie không được ghi, khởi động lại dev server (Turbopack giữ bản cũ của module dùng chung với proxy).
- **Yêu cầu báo giá (Supabase):** bảng `quote_requests` (migration `20261024080000_create_quote_requests_table.sql`) lưu tên khách, email, quốc gia, bậc học (`thpt|dai_hoc|thac_si`), gói (`co_ban|toan_dien`), giá VND (`bigint`, giá chốt tại thời điểm báo), trạng thái (`cho_duyet|da_duyet|tu_choi`, mặc định `cho_duyet`) và `created_at`. Có PII nên RLS bật, `anon`/`authenticated` bị thu hồi quyền + policy `using (false)`, chỉ `service_role` truy cập (đã kiểm chứng: publishable key nhận 401). **Form báo giá đã hoạt động thật:** `landing/quote-form.tsx` (họ tên, email, quốc gia, bậc học, gói; không thu số điện thoại vì bảng không có cột này) POST `/api/quotes` (`app/api/quotes/route.ts`: giới hạn 5/phút/IP và 30/phút toàn site, kiểm tra bằng `parseQuoteRequest`, lưu bằng `createQuoteRequest` ở `lib/quote-store.ts`) rồi hiển thị đúng mức giá server trả về. **Giá chỉ tính ở server** từ bảng `QUOTE_PRICES` trong `lib/quote.ts` (Cơ bản 15.000.000₫, Toàn diện 30.000.000₫; `servicePackages` và mock admin đều lấy giá từ đây, sửa giá ở một nơi): trường `price`/`status` do trình duyệt gửi bị bỏ qua, trạng thái luôn bắt đầu `cho_duyet`. **Kiểm tra email:** `isValidEmail` (`lib/quote.ts`, dùng chung form và server; không nhận `a@b..com`, `a@b`, dấu chấm đầu/cuối/liền nhau, tên miền có gạch nối ở đầu/cuối, đuôi < 2 chữ cái; chưa hỗ trợ email có ký tự Unicode) — form có `noValidate`, email sai thì hiện lỗi dưới ô nhập (`aria-invalid`), đưa con trỏ về ô email và KHÔNG gửi request; server vẫn kiểm tra lại bằng cùng hàm. Form KHÔNG gửi email thật (thông báo chỉ nói "đã ghi nhận"). **Webhook Make.com:** sau khi lưu thành công, route gọi `after(() => notifyQuoteWebhook(...))` (`lib/quote-webhook.ts`) POST JSON `{event:"quote_request.created", id, customerName, email, servicePackage, servicePackageName, price, createdAt}` tới `QUOTE_WEBHOOK_URL` (builder/poster thuần nằm ở `lib/quote.ts`, có test bằng máy nhận giả). URL để trong biến môi trường (không commit; phải thêm trên Vercel), chỉ nhận https (hoặc http localhost), timeout 8 giây, không theo redirect; thiếu biến thì bỏ qua và ghi cảnh báo; webhook lỗi chỉ ghi log (không in URL/PII), KHÔNG làm hỏng hay chặn yêu cầu đã lưu và không có retry/hàng đợi, nên yêu cầu có thể "lọt" khỏi Make nếu Make lỗi lúc đó. Test cục bộ nhớ trỏ `QUOTE_WEBHOOK_URL` tới localhost, đừng đặt URL thật trong `.env.local` khi thử với dữ liệu giả. **Admin:** `/admin/requests` đọc dữ liệu THẬT qua `listQuoteRequests` (`lib/quote-store.ts`; mới nhất trước, tối đa 200 dòng, giờ Việt Nam), gọi `requireAdmin()` và nằm trong matcher của `proxy.ts` (đặt `ADMIN_PASSWORD` để bật đăng nhập; hiện đang mở). **Nút Duyệt hoạt động thật** (`components/admin/approve-quote-button.tsx`, hai bước xác nhận, chỉ hiện ở dòng "chờ duyệt") → Server Action `approveQuoteAction` (`app/admin/requests/actions.ts`, tự kiểm tra `checkAdminWrite()`, giới hạn 20 lần/phút/IP): (1) kiểm tra `QUOTE_APPROVED_WEBHOOK_URL` đã cấu hình (thiếu thì báo lỗi và KHÔNG đổi trạng thái); (2) chuyển `cho_duyet` → `da_duyet` bằng một câu UPDATE có điều kiện status (`approveQuoteRequest`, bấm đúp/hai admin cùng bấm chỉ một người thành công); (3) POST `{event:"quote_request.approved", id, customerName, email, loginUrl}` tới `QUOTE_APPROVED_WEBHOOK_URL` (khác URL của webhook yêu cầu mới) và ĐỢI kết quả; (4) webhook lỗi thì hoàn tác về `cho_duyet` (`revertQuoteApproval`) và báo admin để bấm lại (nếu Make nhận được nhưng phản hồi quá 8 giây thì có thể gửi trùng, bên nhận nên chống trùng theo `id`). **`loginUrl` là MỘT giá trị cấu hình:** `QUOTE_LOGIN_URL` nếu có, không thì `<NEXT_PUBLIC_SITE_URL>/login` (hoặc địa chỉ website hiện tại); mặc định trỏ tới trang `/login` thật (đăng nhập magic link); khi cần đổi sang link khác chỉ cần đổi `QUOTE_LOGIN_URL` và Redeploy, không đổi code hay Make (trong Make phải dùng biến `loginUrl` từ webhook chứ không gõ cứng link) (`resolveLoginUrl` ở `lib/quote.ts`, có test). Link hiện là link chung, chưa gắn riêng từng khách. **Nút Từ chối = XOÁ VĨNH VIỄN yêu cầu** (`components/admin/reject-quote-button.tsx`, hai bước xác nhận) → Server Action `rejectQuoteAction` (tự kiểm tra `checkAdminWrite()`, giới hạn 30 lần/phút/IP) → `deletePendingQuoteRequest`: câu DELETE có điều kiện `status = 'cho_duyet'` nên không xoá nhầm yêu cầu vừa được người khác duyệt; không gửi gì sang Make hay cho khách, và trạng thái `tu_choi` hiện không được dùng (xoá thay vì đánh dấu). Dòng đã duyệt không còn nút thao tác. **Lưu ý khi thử:** `.env.local` đang chứa URL webhook THẬT nên mọi lần bấm Duyệt khi chạy `npm run dev` đều gửi sang Make thật (Make trả HTTP 410 khi webhook ở chế độ Run once đã dùng hết hoặc scenario đang tắt). Webhook chỉ GỬI DỮ LIỆU sang Make; việc gửi email cho khách/nội bộ phải làm bằng module trong scenario Make (code của site không gửi email).

## UI conventions

- **shadcn/ui style `base-nova` trên nền Base UI** (`@base-ui/react`, không phải Radix) — cấu hình ở `components.json`. Thêm component mới bằng CLI `npx shadcn add <name>` vào `components/ui/`; API của Base UI khác Radix: dùng prop `render={<Link .../>}` thay cho `asChild` (xem `landing/hero.tsx`).
- Icon dùng `lucide-react`; animation dùng `motion`; class merge qua `cn()` trong `lib/utils.ts`.
- **Theme/Tailwind v4:** không có `tailwind.config`; token màu và radius khai báo trong `app/globals.css` (`@theme inline` + CSS variables dạng oklch). Có block `.dark` nhưng UI landing/admin được thiết kế cho light theme.
- Ảnh remote chỉ cho phép host `images.unsplash.com` (`next.config.ts`); host khác phải thêm vào `remotePatterns`.
- Định dạng tiền VND dùng `toLocaleString("vi-VN") + "₫"` (helper `formatVnd` hiện được định nghĩa lặp trong `admin/requests/page.tsx` và `landing/quote-form.tsx`).
